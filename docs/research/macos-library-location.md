# Where a macOS app should put a user-visible Library by default

Researched 2026-10-29. The question: where should Carbon put its Library (one Markdown Transcript per Meeting, see [ADR-0002](../adr/0002-json-index-plus-markdown-library.md)) by default? The candidates are `~/Documents/Carbon`, `~/Carbon` at the home root, `~/Library/Application Support/Carbon`, iCloud Drive, or a folder the person picks on first run. For each, what privacy (TCC) prompt does a non-sandboxed, Developer ID–signed app get?

The trigger: on a fresh code identity, the first read of `~/Documents/Carbon` showed "Carbon would like to access files in your Documents folder". Carbon reads the Library on the main thread at launch, so the app froze behind that prompt before its onboarding window appeared.

Sources are Apple documentation, Apple WWDC transcripts, and the apps' own docs or source code, pinned at a commit. Anything I concluded myself, rather than read in a source, is marked **(inference)**. Anything no primary source settles is marked **unverified**. One secondary source, Eclectic Light's tests on macOS 26.4, is used only where Apple is silent, and is labelled as such.

## Short answer

| Location | Visible to the person and an agent? | TCC prompt for a non-sandboxed app | Apple's guidance |
|---|---|---|---|
| `~/Documents/Carbon`, created by default | Yes | **Yes**, on the first read of contents the app has no consent for, which includes any file left by an earlier code identity. Writing new files does not prompt. | Apps "must not write files to [Documents, Desktop, …] unless explicitly directed to do so by the user." |
| `~/Documents/Carbon` (or any folder), **picked by the person in an `NSOpenPanel`** | Yes | **No.** Picking it is "user intent" and grants access "right away and any time in the future". | Matches "explicitly directed to do so by the user". |
| `~/Carbon` (home root) | Yes | **None documented.** Apple lists no home-root location as protected, and secondary tests found none. | Not addressed. The guide lists the standard home subfolders but neither sanctions nor forbids a new top-level folder. |
| `~/Library/Application Support/Carbon` | Hidden (`~/Library` is hidden since 10.7) | No, for the app's own non-container folder **(inference)**. | Meant for "app data files except those associated with the user's documents", "hidden from the user". |
| iCloud Drive (app's ubiquity container) | In Finder › iCloud Drive | iCloud Drive is a protected location. The app's own container needs the iCloud entitlement and a provisioning profile, both available to Developer ID. | Suggested as a default by the HIG only in passing. |

**Recommendation for Carbon:**

1. Keep `~/Documents/Carbon` as the *suggested* location, but make choosing it an onboarding step. Show the folder, and when the person confirms, open an `NSOpenPanel` already pointed at `~/Documents`, with "Carbon" created and preselected, so they confirm it in the panel. That is user intent. It grants lasting access with no TCC prompt, no `NSDocumentsFolderUsageDescription` and no security-scoped bookmark, because Carbon is not sandboxed. It also follows Apple's rule that apps write to Documents only when the user directs it. Obsidian creates vaults this way, and iA Writer adds folders this way.
2. Add `NSDocumentsFolderUsageDescription` anyway, as a safety net. If Carbon ever reads Documents without that consent, for example after a signing change, the prompt then explains itself.
3. Never touch the Library before onboarding has finished. Do every Library read and enumeration off the main thread. A TCC file prompt blocks the *calling thread* until the person answers.
4. `~/Carbon` is the fallback if you want zero prompts with no picker. It is prompt-free as far as anyone has documented, and an agent can find it easily. Its costs are an unusual top-level folder in the home directory and no Apple blessing (Logseq does it: `~/logseq/graphs`). Application Support contradicts ADR-0002's "visible folder an agent can grep". Anarlog has just moved there, but it now relies on Markdown *export* to reach a visible folder, which is the very split ADR-0002 avoids.

## 1. Which locations are TCC-protected for a non-sandboxed app

- **The Apple list.** Since macOS 10.15 the system makes sure apps "have obtained user consent before accessing files in Documents, Downloads, Desktop, iCloud Drive, and network volumes". The Files and folders entry "Includes Desktop, Documents, Downloads, network volumes, and removable volumes" ([Apple Platform Security, Controlling app access to files](https://support.apple.com/guide/security/controlling-app-access-to-files-secddd1d86a6/web)). The Mac User Guide names the same three folders: "Some apps and websites can access files and folders in your Desktop, Downloads, and Documents folders" ([Control access to files and folders on Mac](https://support.apple.com/guide/mac-help/control-access-to-files-and-folders-on-mac-mchld5a35146/mac)).
- **WWDC19 adds third-party cloud storage and Trash.** Desktop and Documents were "prime candidates for protection since that's the default location where many users store their files". Protection also covers "documents stored in iCloud Drive or third-party cloud storage providers or on removable volumes" and network-attached storage. The recap lists "desktop documents downloads, their iCloud Drive or third-party storage, removable network volumes and, of course, trash" ([WWDC19 701, Advances in macOS Security](https://developer.apple.com/videos/play/wwdc2019/701/)).
- **One usage key per protected category.** The Info.plist keys for files and folders are `NSDesktopFolderUsageDescription`, `NSDocumentsFolderUsageDescription`, `NSDownloadsFolderUsageDescription`, `NSNetworkVolumesUsageDescription`, `NSRemovableVolumesUsageDescription`, `NSFileProviderDomainUsageDescription` and `NSFileProviderPresenceUsageDescription`. None of them covers the home folder or `~/Library` ([Protected resources](https://developer.apple.com/documentation/bundleresources/protected-resources)).
- **macOS 14 Sonoma: other apps' containers.** "macOS ensures that they give permission before an app can access data in an application data container from a different developer". It is triggered "when your app accesses a file in another app's data container" ([WWDC23 10053, What's new in privacy](https://developer.apple.com/videos/play/wwdc2023/10053/)). The key is `NSAppDataUsageDescription`: "why the app needs to access files in other apps' sandbox containers" ([Protected resources](https://developer.apple.com/documentation/bundleresources/protected-resources)). A non-sandboxed app's own `~/Library/Application Support/Carbon` is not a container, so reading it does not trigger this **(inference)**.
- **The home root and `~/<App>`.** No Apple source lists them as protected (sources above). Apple never states outright that they are *unprotected*, so this rests on the lists being complete **(inference)**. A secondary source tested macOS 26.4 by listing and reading folders from code. It found that only Desktop, Documents and Downloads "conform to the standard control", with iCloud Drive, removable and network volumes handled separately, and "no evidence of any other special locations among other standard folders in the user's Home folder" ([Eclectic Light, 2026-04-15](https://eclecticlight.co/2026/04/15/privacy-which-folders-are-protected-in-tahoe/), secondary). It did not test a custom `~/<App>` folder.
- **macOS 15 and 26 changes.** I found no Apple documentation that changes the Files and Folders list after Sonoma (**unverified**, see Open questions).

## 2. What triggers the prompt, and what avoids it

- **Writing does not prompt. Reading existing contents does.** "User consent is not required for an app to create new documents in any of these protected locations, just to read existing contents" ([WWDC19 701](https://developer.apple.com/videos/play/wwdc2019/701/)).
- **Files the app created are exempt.** "If your app creates a new file in the Documents folder, the app can access that file without user consent" ([NSDocumentsFolderUsageDescription](https://developer.apple.com/documentation/bundleresources/information-property-list/nsdocumentsfolderusagedescription)).
- **"The app" means its code identity.** macOS records the app's designated requirement (DR) and checks later versions against it. "Ad hoc signed code … has a DR but it's tied to that specific version of the code". An Apple Development build "gets a different DR than a distribution build signed with your Developer ID" ([TN3127, Inside Code Signing: Requirements](https://developer.apple.com/documentation/technotes/tn3127-inside-code-signing-requirements)).
- **Why Carbon prompted.** A fresh code identity sees `~/Documents/Carbon` as files someone else created, so its first read prompts **(inference)**. TN3127 shows the DR mechanism with the microphone, not files. That the "files the app created" exemption is also keyed by DR is **(inference)**. Shipped Developer ID updates share one DR, so a person updating Carbon should not see the prompt again for a folder Carbon created, but **unverified** for files.
- **User intent replaces consent.** Intent is "inferred when double clicking on files in Finder, when dragging and dropping from another application or when selecting files in an Open or Save panel … your app gets access to the file or files that the user selected without the need for a consent prompt" ([WWDC19 701](https://developer.apple.com/videos/play/wwdc2019/701/)). Apple's key page says the same, and adds that the app "can access that file right away and any time in the future" ([NSDocumentsFolderUsageDescription](https://developer.apple.com/documentation/bundleresources/information-property-list/nsdocumentsfolderusagedescription)). Both texts speak of *files*. That picking a *folder* covers files later added inside it is **(inference)**. Eclectic Light observed an app regaining Documents access through an Open panel even after the person had turned the Files & Folders switch off ([Eclectic Light](https://eclecticlight.co/2026/04/15/privacy-which-folders-are-protected-in-tahoe/), secondary).
- **Panel delegates don't count.** URLs passed to `NSOpenSavePanelDelegate` callbacks "may trigger user consent prompts, because … they haven't selected the file yet" ([WWDC19 701](https://developer.apple.com/videos/play/wwdc2019/701/)).
- **Security-scoped bookmarks are a sandbox mechanism.** `withSecurityScope` is "for use in an app that adopts App Sandbox" ([NSURL.BookmarkCreationOptions.withSecurityScope](https://developer.apple.com/documentation/foundation/nsurl/bookmarkcreationoptions/withsecurityscope)). `startAccessingSecurityScopedResource()` works "in an app that has adopted App Sandbox" ([docs](https://developer.apple.com/documentation/foundation/nsurl/startaccessingsecurityscopedresource())). A non-sandboxed app can store the path, as Carbon's `SettingsKey.libraryFolder` already does. Use a plain bookmark only if you want to follow the folder when it is moved **(inference)**.
- **The usage string customizes the prompt but can't avoid it.** "Add the NSDocumentsFolderUsageDescription key … to provide a message that explains why your app needs access. The usage description is optional, but highly recommended". The choice is remembered and reset with `tccutil reset SystemPolicyDocumentsFolder <bundleID>` ([NSDocumentsFolderUsageDescription](https://developer.apple.com/documentation/bundleresources/information-property-list/nsdocumentsfolderusagedescription)). Carbon's `project.yml` declares no such key today (`project.yml` L51-L56).
- **iCloud Drive for a Developer ID app.** "iCloud: iCloud documents" is ticked for Developer ID ([Supported capabilities (macOS)](https://developer.apple.com/help/account/reference/supported-capabilities-macos)). The container must be declared in `com.apple.developer.ubiquity-container-identifiers` ([url(forUbiquityContainerIdentifier:)](https://developer.apple.com/documentation/foundation/filemanager/url(forubiquitycontaineridentifier:))). Would Carbon reading its *own* ubiquity container prompt as "iCloud Drive"? **Unverified.**

## 3. Apple's placement guidance

- **Home subfolders are for the person's files.** The guide lists the typical home subfolders (Applications, Desktop, Documents, Downloads, Library, Movies, Music, Pictures, Public, Sites) and says: "The preceding directories are for storing user documents and media only. Apps must not write files to the preceding directories unless explicitly directed to do so by the user. The sole exception to this rule is the Library directory". It also says: "The files in the user's Documents and Desktop directories should reflect only the documents that the user created and works with directly … must never be used to store data files that your app creates and manages automatically" ([File System Programming Guide, File System Basics](https://developer.apple.com/library/archive/documentation/FileManagement/Conceptual/FileSystemProgrammingGuide/FileSystemOverview/FileSystemOverview.html), archived).
  - Transcripts are generated by Carbon, but they are the person's documents, which they read, edit and hand to an agent. A default under Documents fits the guide best when the person has chosen it **(inference)**.
  - The guide says nothing about new top-level folders in the home directory.
- **Application Support is for app data, hidden from the person.** It holds "all app data files except those associated with the user's documents", and "files that the app uses to run but that should remain hidden from the user". `Library` is "hidden in macOS 10.7 and later" ([same guide](https://developer.apple.com/library/archive/documentation/FileManagement/Conceptual/FileSystemProgrammingGuide/FileSystemOverview/FileSystemOverview.html)). That suits `meetings.json`, which is where Carbon keeps it, not the Transcripts.
- **The HIG sets no default location.** It only says a browser can open on "a Documents or iCloud folder or the most recently selected location", and that a save interface "defaults to a logical location to help people place the saved document where they want" ([HIG, File management](https://developer.apple.com/design/human-interface-guidelines/file-management)).

## 4. Keeping a prompt from freezing launch

- **A file prompt blocks the thread that asked.** For these consent prompts, "rather than denying the access and displaying an alert to the user, the calling thread is actually blocked, waiting for the user to approve or deny". On a similar case: "if a prompt is displayed, the calling thread is blocked waiting for the user's interaction, so you wouldn't want to call this on your app's main thread" ([WWDC19 701](https://developer.apple.com/videos/play/wwdc2019/701/)). The first quote is said about the Mojave categories and introduces the Catalina file categories, which work the same way **(inference)**. That fits the freeze Carbon saw.
- **Keep the main thread for UI.** "Make sure your app uses the main thread only to interact with the user interface … Direct all other operations to a background thread", and "Don't synchronize the main thread with a background thread" ([Improving app responsiveness](https://developer.apple.com/documentation/xcode/improving-app-responsiveness)).
- **Same advice for iCloud.** Apple says not to call `url(forUbiquityContainerIdentifier:)` on the main thread, and to check `ubiquityIdentityToken` at launch instead ([docs](https://developer.apple.com/documentation/foundation/filemanager/url(forubiquitycontaineridentifier:))).
- **Check without prompting.** WWDC19 says "apps can test whether a given file is readable or writable without triggering consent prompts using these APIs", but the API names are only on a slide, not in the transcript (**unverified** which ones).
- **Ask when the reason is obvious.** About Sonoma's app-data prompt, Apple says: "If the timing of the prompt is surprising, or the purpose is unclear, your app's access might be denied" ([WWDC23 10053](https://developer.apple.com/videos/play/wwdc2023/10053/)). The same logic argues for any Documents prompt appearing inside onboarding, not at launch **(inference)**.
- **Anarlog shows a native alert during slow startup work** so launch never looks hung ([A apps/desktop/src-tauri/src/startup.rs#L211-L215](https://github.com/fastrepl/anarlog/blob/a7dadfbb9477177723cab1e140ae06b4e868ecc5/apps/desktop/src-tauri/src/startup.rs#L211-L215)).

Two patterns stand out **(inference)**:

- **Database-backed apps** (Bear, Day One, MacWhisper, Granola, Copper, and now Anarlog) keep the store hidden in `~/Library` and never prompt.
- **Apps whose store is plain files the person owns** (Obsidian, iA Writer, Logseq's old file graphs) either let the person pick the folder or use iCloud. Logseq's current default sits at the home root.

None of the apps I checked defaults silently to `~/Documents/<App>`.

## Open questions and things I could not verify

- **Is `~/Carbon` prompt-free?** I could not test it. A small ad-hoc-signed probe app, built to list `~`, a new `~/<probe>` folder and Application Support, would not launch from this agent's shell (`open` returned LaunchServices error -10825). Apple's lists and Eclectic Light's tests point to no prompt, but neither tested a custom home-root folder.
- **Does picking a folder cover what is added to it later?** Apple's wording covers "files". I expect the folder pick to cover later contents and survive Developer ID updates, but I have not checked it on macOS 26. Test it: pick `~/Documents/Carbon` in a panel, relaunch, add a file from Finder, and enumerate.
- **Is the "files the app created" exemption tracked per file, and does it survive a new identity?** Apple documents no mechanism. The undocumented `com.apple.macl` extended attribute is widely assumed to carry it. Carbon's prompt on a fresh identity suggests the exemption is bound to the DR **(inference)**.
- **Did macOS 15 or 26 change the Files and Folders list?** I found no Apple source for either.
- **Which APIs test access without prompting?** WWDC19 names them only on a slide.
- **Granola's and Apple Notes' storage** have no first-party documentation.
